## 一、项目目标

用 YOLO 做视觉识别，并且把它做成一个**能自主决策的 Agent**（Harness），
而不是"跑一次就结束的脚本"。

围绕这个目标做了四块能力：

| 模块 | 做了什么 |
|---|---|
| 识别 | YOLO 物体检测（图片 / 文件夹监控 / 摄像头实时） |
| 认人 | 人脸识别（认出熟人、登记陌生人、抓拍留证） |
| 对话 | 接入大模型，用中文指挥它调工具 |
| 数据 | 自己打标签 + 训练专属模型 |

## 三、踩过的坑（重点）

### 坑 1：AI 会跟自己的旧话保持一致，导致记忆被永久污染

**现象**：AI 反复说"我没有记忆""每次对话都是独立的"，即使提示词里已经明确写了"你有记忆"。

**排查过程**：
1. 先怀疑记忆没存上 → 抓发包验证，**14 条历史确实发出去了**，排除
2. 再怀疑提示词不够强 → 把提示词改得更硬，**还是否认**
3. 最后把记忆文件逐条打印出来，看到真相：

```
[2] assistant : 我没有关于之前对话的记忆...
[4] assistant : 我这边确实没有上次识别的记录...
[6] assistant : 我没有上次识别的记忆...
[8] assistant : 我真的没有上次的对话记录...
```

**根因**：模型决定怎么回答时，**最有力的证据是"它自己刚刚是怎么说的"**。
历史里已经否认了 4 次，第 5 次它当然继续否认 —— 一条系统提示词压不过上下文里 4 次自我否认。
**而且这形成了正反馈**：越否认，历史里的否认记录越多，就越难纠正。

**解决**：把历史里那些"自我否认"的轮次删掉，只保留有效内容。
清完之后立刻正常，能正确答出"上次聊的是华南理工大学"。

**教训**：Agent 的记忆不只是"存下来"，还要**保证存进去的东西不会自我强化错误**。

### 坑 2：工具调用链断裂，接口直接报 400

**现象**：
```
Error code: 400 - An assistant message with 'tool_calls' must be followed by
tool messages responding to each 'tool_call_id'.
```

**根因**：OpenAI 格式有个硬规定 —— assistant 消息里带了 `tool_calls`，
后面就必须紧跟对应的 `tool` 回复。而我写的**记忆裁剪函数在截断对话时，
会把"AI 决定调用工具"和"工具返回结果"从中间切开**，留下一个"孤零零的工具调用"。

这种残缺记录怎么来的？调用工具的过程中被打断（Ctrl+C、程序崩了、
摄像头模式把终端占了），"要调工具"那句话留下了，回复永远没来。然后**它被存进记忆**，
之后每次启动都报错。

**解决**：写了 `_drop_orphan_tool_messages()`，做三件事：
1. 找出"说了要调工具却没收到回复"的 assistant 消息 → 摘掉它的 `tool_calls`（有正文就留正文）
2. 删掉没有对应 `tool_calls` 的孤立 `tool` 回复
3. **在发请求前再体检一次**，并且启动时发现坏记忆就**自动清理并写回文件**（自愈）

**教训**：凡是"两个消息必须成对出现"的数据结构，裁剪时都要小心别拆散它们。

### 坑 3：人脸识别阈值调不对（用错了基准数据）

**现象**：人脸识别"不准"，认不出同一个人。

**排查过程**：一开始以为是阈值问题，就在自己的图上调。结果越调越糊涂 ——
把阈值调到 0.25 才勉强能认出"同一人"，但这时**不同人之间也开始互相误认**。

**根因**：我调的基准数据是**卡通/带口罩的图**。
SFace 是在真人照片上训练的，对这种图给出的相似度分布本身就是畸变的。

**解决**：换真人照片（OpenCV 官方样例合影，一张图 92 张脸）重新做量化评测：

| 场景 | 实测相似度 |
|---|---|
| 同一个人（仅亮度/缩放/平移扰动） | 最低 0.859，平均 **0.940** |
| 不同人之间（45 对） | 最高 0.356，平均 0.135 |

**结论**：同人 0.94 vs 异人 0.14，**分得非常开**，官方阈值 0.363 误认率是 0%。
所以"不准"根本不是阈值问题。

**真正的病根**：40 次同人对比里有 **10 次压根没检出脸**。
那张合影上脸从 150×188 一路小到 **8×11 像素** —— SFace 对小于 40 像素的脸，
特征基本是噪声。

**解决**：
1. 加**小脸门槛**：小于 60 像素的脸不参与认人，画面上显示灰框"too small"。
   宁可说"太远认不准"，也不要瞎认。
2. **提高人脸检测召回**：把 YuNet 的置信度门槛从 0.7 降到 0.5，
   让侧脸/模糊脸先被检出来
3. **多帧投票**：新面孔连续 3 帧都稳定认不出才登记，避免单帧误判污染脸库
4. **每人存多份特征**（最多 3 份），比对时取最像的一份

**教训**：**评测数据选错了，调参就是瞎调。** 先用能代表真实场景的数据量出基线，再动手。

### 坑 4："见面次数"被写成了"每帧 +1"

**现象**：同一张脸在画面里坐几分钟，脸库显示"见过 900 次"。用户反馈："这也太离谱了。"

**根因**：`touch()` 在每一帧都被调用，无条件 +1。
摄像头 5 fps，坐 3 分钟就是 900。

**解决**：改成**只有"离开过又回来"才算一次见面** ——
记录上次出现时刻，中间断开超过 5 秒才 +1。
另外顺便把"累计被看到多少帧"单独记一个 `frames_seen`，用来观察识别稳定性。

**教训**：**计数器要定义清楚"一次"是什么。** "被看到"和"见过一次"是两件事。

---

### 坑 5：命令行版没法一边看摄像头一边打字

**现象**：想在摄像头模式里问 AI 问题，但一开摄像头就没法输入了。

**根因**：`cv2.imshow` 的窗口**必须由主线程刷新**，而 `input()` 会阻塞主线程。
两者只能选一个。

**解决**：用 tkinter 重做界面 —— 摄像头跑在**后台线程**，
画面转成图片画进窗口标签里。这样主线程空出来接输入，两边就能同时进行了。

**教训**：选技术方案时要先想清楚"哪个操作会霸占主线程"。

### 坑 6：按帧数猜时间（老代码的经典错误）

**现象**：`harness_camera.py` 里设了"每 5 秒抓一帧"，实际约每 **1.7 秒**就抓一次。

**根因**：
```python
if frame_count % (CAPTURE_INTERVAL * 10) == 0:  # 注释写着"假设 30fps，每5秒约150帧"
```
这段代码假设摄像头恒为 30fps，但：
- 30fps 时：50 帧 ≈ 1.7 秒（不是 5 秒），负载和产出文件是设定的 3 倍
- 15fps 时：又变成 3.3 秒
- 笔记本摄像头会自动降帧，实际值还会飘

**解决**：改成判断**真实经过的秒数**（`elapsed >= CAPTURE_INTERVAL`），
并顺带统计、打印实际帧率。

**教训**：**时间就用时间算，别用帧数换算。** 帧率是不受你控制的变量。

### 坑 7：同一秒保存多张，后写的把先写的覆盖了

**现象**：文件夹监控一次发现多张新图时，磁盘上只剩一个结果文件。

**验证**：写了个复现脚本，同一秒保存 3 张 —— 磁盘上确实只有 1 个文件，
内容是第 2 张的，**前两张的检测结果永久丢失**。

**根因**：文件名只用秒级时间戳（`%Y%m%d_%H%M%S`），同一秒内必然同名，
而写入用的是 `"w"` 模式，直接覆盖。

**解决**：两层保险 ——
1. 时间戳加微秒（撞车概率降到几乎为零）
2. 万一还撞上（同名文件已存在），加序号 `_1` `_2` 直到不重名

**教训**：**凡是"自动生成文件名"的地方，都要问一句"生成两次会不会同名"。**

---

### 坑 8：AI 达到工具调用轮数上限，任务半途而废

**现象**：让它"把所有图都识别一遍并总结"，它可能一轮只识别一张，
到第 8 轮就被强制中断，用户看不到最终答复。

**根因**：`for round_num in range(8)` 是硬编码上限，而且中断时的提示写着
"你可以再说一次，或者换个说法" —— 这**会误导用户重新提问，把已经干完的活重做一遍**。

**解决**：
1. 上限提为常量 `MAX_AGENT_ROUNDS`（默认 12，可用环境变量覆盖）
2. 中断提示改成："已经执行的结果都保留着，**你直接说「继续」我就接着往下做**"
3. 把该提示写入对话历史，使下一轮能自然衔接（实测有效：说"继续"后 AI 会接着调工具）

**教训**：**"任务没做完"要说清楚，而且要给用户一个正确的下一步动作**，
不能给一个会让他做无用功的提示。

## 五、当前的真实瓶颈

**1. 没有可用的 GPU，训练基本不可行**

一开始判断"没有显卡"，后来发现是**判断错了一半**：

| | 情况 |
|---|---|
| CUDA（NVIDIA） | ❌ 确实没有 |
| **AMD Radeon R7 M260** | ✅ **有这块独显，2GB 显存** |
| 能不能用 | ❌ **不能用** —— 2013 年的卡 + 2020 年的驱动，Ollama 走 Vulkan 一加载就崩（见坑 10） |
| Intel HD 5500 核显 | 性能太弱，跑不动训练 |

```
torch 2.14.1+cpu    CUDA 可用: False    CPU: i5-5200U（低功耗双核）
```

实测估算：150 张图 × 50 轮 ≈ **5~7 小时**；有可用显卡只要几十分钟。
这是硬件限制，不是代码问题。

**2. 本地小模型偏慢，但没想象中慢**

qwen2.5:1.5b（CPU 模式）：
- 直接调 Ollama：短回复约 **1.5~8 秒**
- 经 n8n 走一圈：约 **1.5~3.4 秒**（n8n 的开销几乎可以忽略）

之前记的"一轮带工具调用 54 秒"是**模型刚加载 + 多次工具往返**时的最坏情况，
模型常驻内存后会快很多。

**3. 数据标注是最费人力的环节**
要训出能用的模型，每个类别至少需要 50~150 个框。这是纯人力投入。

## 六、n8n 编排平台（任务一.2）

### 做了什么

用 **n8n** 搭了一条"本地大模型接口"，把本地 Ollama 包成一个 HTTP 接口：

```
你的程序  ──POST {"message":"..."}──>  n8n Webhook (/webhook/agent)
                                             │
                                             ▼
                                    HTTP Request 节点
                                             │  POST /api/chat
                                             ▼
                                    本地 Ollama (qwen2.5:1.5b)
                                             │
                                             ▼
                                     回答原路返回
```

**实测**：首次调用 3.4 秒（要加载模型），之后稳定 **1.5~1.6 秒**。

### 一个关键决定：用代码建工作流，而不是在界面上点

| | 界面点出来 | 代码建（本项目选这个） |
|---|---|---|
| 存在哪 | n8n 的数据库里 | **JSON 文件，进 git** |
| 别人能否复现 | ❌ 看不到 | ✅ `python create_workflow.py` 一条命令重建 |
| 能否 diff | ❌ | ✅ |

所以工作流定义导出成了 `n8n_workflows/local_llm_agent.json`。

### 坑 9：装 n8n 踩了 7 个坑（这条机器上尤其曲折）

**这个坑很长，但每一步都能复现，值得记下来。**

**① npm 官方源在国内基本不可用**

```
registry.npmjs.org        20087ms 超时
registry.npmmirror.com      472ms 正常      ← 差 40 倍
```

**② `sqlite3` 是原生模块，装不上**

n8n 依赖 `sqlite3`，它是 C++ 扩展，安装时要：
- 要么下载**预编译二进制**
- 要么用 **node-gyp 现场编译**

两条路都要访问国外站点，都失败。

**③ prebuild-install 认不出 Node 24**

```
prebuild-install warn This package does not support N-API version undefined
```

Node 24 实际支持 N-API 10（`process.versions.napi = 10`），
但 `prebuild-install` 版本太老读不出来，于是放弃下载、转去编译。

**④ 编译又缺 Visual Studio**

```
gyp ERR! stack Error: Could not find any Visual Studio installation to use
```

为了一个 1.8MB 的 `.node` 文件去装几个 GB 的 C++ 工具链，不划算。

**⑤ 最终解法：跳过编译，手动塞入预编译二进制**

```bash
# 跳过所有编译脚本
npm install -g n8n --ignore-scripts --registry=https://registry.npmmirror.com

# 把现成的二进制放到它该在的位置
# 从镜像下载 sqlite3-v5.1.7-napi-v6-win32-x64.tar.gz
# 解压后得到 build/Release/node_sqlite3.node
# 复制到 node_modules/sqlite3/build/Release/
```

验证：`node -e "require('sqlite3')"` 能真正执行 SQL 才算成功。

**⑥ 中途还遇到 DNS 偶发解析失败**

```
prebuild-install warn install getaddrinfo ENOTFOUND registry.npmmirror.com
```

但同一时刻 PowerShell 测同一个域名是通的 —— 说明是**偶发**。
加 `--dns-result-order=ipv4first` 缓解。

**⑦ 网络怪现象的元凶：hosts 文件被劫持**

排查推送失败时发现的：

```
127.0.0.1 github.com
127.0.0.1 api.github.com
127.0.0.1 raw.githubusercontent.com
...（共 30 多条 github 相关域名，全部指向本机）
```

这是**网络加速工具写的屏蔽规则**。它解释了之前一连串怪现象：
`raw.githubusercontent.com` 连不上、git push 超时、但 `ls-remote` 又能通。

**没有去改它** —— 那是用户的网络工具在管，改了会影响其它软件。

**教训**：
- **国内环境装任何 Node/Python 包，先换镜像**，否则可能浪费几十分钟
- 遇到原生模块编译失败，**先想"能不能直接用预编译的"**，别急着装编译工具链
- 网络问题时，**`hosts` 文件一定要查**，它会产生非常反直觉的现象

### 坑 10：Ollama 一推理就崩溃（0xc0000005）

**现象**：Ollama 服务能启动、能列出模型，但**任何推理请求都返回 HTTP 500**：

```json
{"error":"llama-server process has terminated: exit status 0xc0000005:
 The instruction at 0xp referenced memory at 0xp. The memory could not be s."}
```

`0xc0000005` 是 Windows 的**内存访问违规**（段错误）。

**排查**：翻 Ollama 启动日志，看到了关键一行：

```
inference compute ... name="AMD Radeon R7 M260" type=discrete total="2.0 GiB"
```

**Ollama 自动认出了这块 AMD 显卡，并尝试用它跑推理。**

**根因**：这块卡是 **2013 年的 Radeon R7 M260**，驱动是 **2020 年的**，
而新版 Ollama 走的是 **Vulkan** 后端 —— 老卡 + 老驱动 + 新后端，一加载模型就崩。

**解决**：关掉 Vulkan，强制走 CPU：

```bash
set OLLAMA_VULKAN=false
ollama serve
```

**结果**：立刻正常，短回复约 8 秒。

**教训**：
- **"有显卡"不等于"显卡能用"**。老硬件 + 新软件的组合经常出问题
- **崩溃时先看服务端日志**，它会明确告诉你它选了哪个后端、用了哪块设备
- 反直觉但有效：**关掉 GPU 反而能跑起来**

---

### 结论：n8n 和自研代码的分工在哪

把 n8n 接进 `agent.py` 之后（加了 `--provider n8n`），同一个 Agent 有了三条路，
**能力并不等价**，这个对比结果本身就是这节最有价值的产出：

| 后端 | 调用链 | 聊天 | **调工具** | 速度 |
|---|---|---|---|---|
| `local` | 直连 Ollama | ✅ | ✅ 9 个工具全可用 | 1.5~8 秒 |
| `cloud` | 直连 DeepSeek | ✅ | ✅ 9 个工具全可用 | 1~3 秒 |
| `n8n` | 经 n8n 中转 | ✅ | ❌ **不支持** | 2~6 秒 |

**为什么 n8n 那条做不了工具调用？**

不是配置问题，也不是偷懒，而是**图形化编排的固有边界**：

工具调用的本质是一个**循环**：

```
模型说"我要调工具" → 执行工具 → 把结果喂回模型 → 模型再判断 → …
（直到模型给出最终答复）
```

在代码里这就是一个 `for` 循环（本项目是 `MAX_AGENT_ROUNDS` 轮）。
但在 n8n 里，要表达"根据模型输出决定是否回到上一步"，
你得拖出一堆 IF 节点 + 回环连线，最后变成一张**很难看懂、更难维护的蜘蛛网**。

**n8n 自己也知道这一点** —— 它内置了 `Code` 节点，因为复杂逻辑本来就该用代码写。

**所以真正的分工是：**

```
┌────────────────────────────────────────────────────┐
│  业务逻辑层：判断、循环、状态、自己的算法           │
│  → 用代码。这里是代码的绝对优势                     │
├────────────────────────────────────────────────────┤
│  集成层：连第三方服务、处理账号授权和协议            │
│  → 用 n8n。这里是 n8n 的绝对优势（400+ 连接器）     │
└────────────────────────────────────────────────────┘
```

**n8n 真正的主场是这种活**：

> 收到带附件的邮件 → 存网盘 → 记进表格 → AI 分析 → 结果发到钉钉

自己写代码的话，光是 Google 三件套的 OAuth 授权就要折腾半天，
而这跟业务毫无关系 —— n8n 把这些"接线活"变成了点几下。

**而本项目的核心能力**（YOLO 识别、人脸识别、摄像头、打标签）
**都是自己写的内部工具**，n8n 里没有现成连接器 —— 这恰恰是它帮不上忙的地方。

**教训**：
- **低代码工具不是"更好的写代码方式"，它解决的是另一类问题**
- 判断标准很简单：**你要连的东西是"别人的服务"还是"自己的代码"？**
- 体会一个工具的**边界**，比学会它的**用法**更重要

---

### 坑 11：n8n 表达式写错，模型收到的是"模板代码"
**现象**：Webhook 通了、HTTP 200、有返回，但**模型的回答驴唇不对马嘴**：

> "抱歉，我不太明白你的问题，你可能是输入了错误的信息"

**根因**：我在 HTTP Request 节点的 JSON body 里这样写：

```json
{ "messages": [ { "role": "user", "content": "={{ $json.body.message }}" } ] }
```

n8n **没有求值这个表达式**，把 `={{ $json.body.message }}` 当成**普通字符串**原样发给了 Ollama。
模型收到的用户消息字面上就是那串模板代码，于是回"你输入了错误的信息"。

**解决**：把**整个 jsonBody 写成一个表达式**，用 `={ ... }` 包住：

```javascript
={{ {
  model: 'qwen2.5:1.5b',
  stream: false,
  messages: [
    { role: 'system', content: '你是一个视觉识别助手…' },
    { role: 'user', content: $json.body.message }
  ]
} }}
```

改完立刻正常：问"1+1 等于几"答"1+1 等于2"。

**教训**：
- HTTP 200 且返回结构正常 **不代表内容对** —— 要**看内容**，不要只看状态码
- 模板引擎的求值范围很关键：**有时候必须把整个对象包成表达式，而不是只包一个字段**
- 排查这类问题时，"模型回复驴唇不对马嘴"是个强烈信号：**先怀疑它收到的输入**，而不是模型能力

## 七、桌面应用（任务一.2 / 二.3）

### 做了什么

用 **Electron** 把它包成一个真正的桌面窗口：

```
Electron 窗口
    │  加载 http://127.0.0.1:8765
    ▼
web_server.py（Python 后端，只用标准库 http.server）
    ├── /video     MJPEG 视频流（<img> 标签直接显示）
    ├── /stats     人脸数 / 脸库人数 / 帧率
    ├── /chat      转发给 AI
    └── /snapshot  存图
```

双击 `启动桌面应用.bat` 就能用。Electron 会**顺手把 Python 后端拉起来**，
关窗口时把后端一起收掉，不留后台进程。

### 为什么选 Electron 而不是 Tauri

| | Tauri | Electron |
|---|---|---|
| 依赖 | **需要 Rust 工具链** | 只需要 Node（本机已有） |
| 本机情况 | ❌ 没有 `cargo`/`rustc`，装它要下 1~2 GB | ✅ node v24 就绪 |
| 包体积 | 小（几 MB） | 大（150 MB 二进制 + 380 MB 解压后） |

本机网络很差（装 n8n 时踩了一串坑），**再下 1~2 GB 的 Rust 工具链风险太高**，
所以选了 Electron。这是个务实的取舍，不是技术上谁更优。

### 为什么后端不用 FastAPI / Flask

**因为能少装就少装。** Python 标准库的 `http.server` 已经够用：

- **MJPEG 视频流**：`multipart/x-mixed-replace` 这个格式很老，但浏览器
  把它当"会自己变的图片"，所以一行 `<img src="/video">` 就能看到实时画面 ——
  不用 WebSocket、不用前端流处理代码
- **JSON 接口**：几十行手写路由就够了

结果：**后端零额外依赖**，前端零框架、零构建步骤。

### 坑 12：Electron 窗口起不来（`app` is undefined）

**现象**：启动 Electron 后立刻退出，报：

```
TypeError: Cannot read properties of undefined (reading 'requestSingleInstanceLock')
    at Object.<anonymous> (main.js:134:21)
    at Module._compile (node:internal/modules/cjs/loader:1937:32)
```

**关键线索在堆栈里**：`node:internal/modules/cjs/loader` 是 **Node.js 的模块加载器**。
如果 Electron 正常运行，堆栈里应该是 Electron 自己的东西。

也就是说：**Electron 是按"纯 Node 脚本"跑的，根本没进入图形界面环境**，
所以 `require("electron")` 拿不到 `app` 对象。

**根因**：环境变量 **`ELECTRON_RUN_AS_NODE=1`**。

这个变量本来是给"我想用 Electron 自带的 Node 跑个脚本"这种场景准备的，
一旦设上，Electron 就**完全退化成 node.exe**。

查出来它是**会话级变量**（不是用户/系统级的持久设置），来源大概是某个工具留下的。

**解决**（两层保险）：

1. 启动器里显式清空：`set ELECTRON_RUN_AS_NODE=`
2. `main.js` 开头也检查并删掉它：

```javascript
if (process.env.ELECTRON_RUN_AS_NODE) {
  console.log("[desktop] 检测到 ELECTRON_RUN_AS_NODE，已清除（否则窗口起不来）");
  delete process.env.ELECTRON_RUN_AS_NODE;
}
```

**教训**：
- **报错堆栈里出现 `node:internal/...` 而你明明在跑 Electron —— 这就是信号**：
  程序跑错运行时了，先查 `ELECTRON_RUN_AS_NODE`
- 环境变量能悄悄改变一个程序的行为，排查时**要把环境变量当嫌疑人**

### 坑 13：Web 界面聊天要等 149 秒

**现象**：桌面应用的聊天框发一句话，要等 **149 秒**才出结果。
但同样的模型用命令行调只要 1~2 秒。

**排查**：用同一个 Ollama 接口做对照实验：

| 输入 | 耗时 |
|---|---|
| 只问一句话 | **1.1 秒** |
| 带上完整对话记忆 | **149 秒** ← 130 倍差距 |

**根因**：`agent_memory.json` 里累积了 **61 条消息、正文 3.5 万字（≈1.7 万 tokens）**，
其中**绝大多数是工具调用的原始结果**（整份图片列表、整份识别结果……）。

在 CPU 上让一个 1.5B 的小模型啃 1.7 万 tokens 的 prompt，就是这个下场。

**更深一层的问题**：这些历史对"看着摄像头随问随答"这个场景**毫无价值** ——
里面全是过时的识别结果。

**解决**：Web 会话默认**不加载历史**（另开一个干净会话），
想延续记忆的话加 `--with-memory` 参数。

**结果**：149 秒 → **2~4 秒**。

**教训**：
- **"上下文越长越好"是错觉**。长上下文不只是慢 ——
  如果里面大部分是无关的旧数据，反而会干扰模型
- Agent 的**工具调用结果特别占地方**（一份识别结果动辄几千字），
  把它们长期堆在对话历史里是个设计缺陷
- 对照实验是找性能问题最快的办法：**同一个接口，改一个变量，看差距**

### 坑 14：我自己把摄像头禁掉了

**现象**：用户反馈「桌面应用打开后没摄像头」。

**排查**：先怀疑硬件和驱动，实测却发现一切正常：

```
设备管理器      : Integrated Webcam  状态 OK
OpenCV 打开编号0: 成功，能读到帧
web_server 直启 : camera_ok=True, fps=22, 检测到 1 张脸
```

**根因**：`desktop/main.js` 里 spawn 后端时**写死了 `--no-camera` 参数**：

```javascript
spawn(py, [script, "--port", String(PORT), "--no-camera"], {...})
//                                                ^^^^^^^^^^^^
```

那是早期测试「没有摄像头时怎么调试」时加上的，测试完**忘记改回来**，
结果摄像头明明能用，却被程序自己关掉了。

**解决**：默认开启摄像头，改成用环境变量控制：

```javascript
if (process.env.DESKTOP_NO_CAMERA === "1") args.push("--no-camera");
```

**教训**：
- **「为了测试临时改的代码」必须标记清楚，并尽快改回来** ——
  这种代码最容易混进最终产物，而且它不报错、不崩溃，只是功能悄悄没了
- 排查「功能不工作」时，**先确认「是不是被自己关掉了」**，
  再往下查硬件、驱动、依赖 —— 顺序反了会浪费很多时间
- 硬件探测的成本很低（几十行脚本），**先证伪再深入**
